Controlled Intelligence Invocation, Context Routing, Output Validation, and System Boundaries

1. Document Purpose
This document defines the Bhudhi Architecture and Trigger Router for Torgima Phase 1. Bhudhi is the controlled intelligence layer that interprets system state, structures user input, drafts allowed outputs, and assists execution without becoming the authority of the system.
The Trigger Router determines when Bhudhi is allowed to run, which Bhudhi mode is used, what context is provided, what output schema is required, and which validation checks must pass before the output can be used. Bhudhi must never be called casually from random API routes, frontend components, or engines. Every invocation must be routed, typed, logged, validated, and bounded by the Control Engine.
Rule: Bhudhi is never an uncontrolled assistant. Bhudhi is a system service that can only operate through approved triggers, approved context packets, approved prompt contracts, and approved output validators.
2. Core Law
Bhudhi interprets and structures execution. It does not govern execution.
Bhudhi cannot decide condition, override enforcement, create unauthorized tasks, change database state directly, approve invalid proof, bypass permissions, or mutate the blueprint without a system-approved mutation path. Its output is advisory or structured until another engine validates and applies it.

4. What Bhudhi Owns
Interpreting user text inside approved system context.
Drafting task titles, task instructions, feedback clarification, recovery language, and explanations.
Classifying user input into predefined categories when routed by an engine.
Summarizing system state in user-facing language.
Suggesting structured outputs that must be validated before use.
Reducing cognitive load by making next actions clearer.
Supporting execution continuity without overriding control rules.
5. What Bhudhi Does Not Own
It does not calculate signals.
It does not determine conditions.
It does not create enforcement packages.
It does not approve or reject permissions.
It does not write directly to database tables other than BhudhiLog/BhudhiMemory through approved services.
It does not mark tasks complete or proof valid.
It does not bypass task generation, feedback validation, dependency checks, or state integrity rules.
It does not invent hidden product behavior outside the current specification.
6. Trigger Router Responsibilities
Receive a typed Bhudhi trigger from an approved system source.
Confirm the trigger is allowed for the user's current condition and enforcement package.
Select the correct Bhudhi mode and prompt contract.
Build the smallest sufficient context packet.
Reject triggers with missing context, stale state, or forbidden purpose.
Route the call to the provider adapter with timeout and usage limits.
Run output validation before returning anything to the caller.
Write BhudhiLog for every attempted invocation.

10. Context Packet Contract
Bhudhi receives only the minimum context required for the trigger. The context packet must be built by the Context Builder, not by ad hoc route logic.
export interface BhudhiContextPacket {  userId: string;  blueprintId?: string;  triggerType: BhudhiTriggerType;  bhudhiMode: BhudhiMode;  stateVersion: number;  condition?: "NOTHINGNESS" | "DANGER" | "STABLE" | "GROWTH";  enforcementPackageId?: string;  allowedActions: string[];  forbiddenActions: string[];  currentOrder?: {    id: string;    type: string;    difficulty: string;    proofType: string;    status: string;  };  userInput?: string;  systemFacts: Record&lt;string, unknown&gt;;  outputContractName: string;  maxTokens: number;}
11. Context Minimization Rules
Do not pass full user history unless the trigger explicitly requires it.
Do not pass raw private notes when a summarized field is sufficient.
Do not pass secrets, tokens, credentials, or internal environment variables.
Do not pass database records that are unrelated to the active trigger.
Always pass allowedActions and forbiddenActions.
Always pass stateVersion so stale outputs can be rejected.
Always pass outputContractName so the validator knows the required schema.

13. Routing Flow
Caller submits a typed BhudhiTriggerRequest.
Trigger Router authenticates the source and trigger purpose.
Router loads current state version, condition, enforcement package, and trigger registry entry.
Router checks eligibility, budget, rate limit, and output contract availability.
Context Builder creates minimal context packet.
Prompt Contract Builder combines system instruction, context, and output schema.
Provider Adapter executes the call with timeout and max token limit.
Output Validator parses and validates schema and rule compliance.
BhudhiLog records status, usage, latency, prompt contract, and output hash.
Validated output is returned to the calling engine.

19. Fallback Behavior
Bhudhi failure must never stop the execution loop. Every trigger must define a deterministic fallback.

Proceed without memory if trigger permits.
20. Security and Permission Rules
Bhudhi cannot be invoked without an authenticated user or approved internal worker context.
Bhudhi cannot receive secrets, private keys, raw tokens, or database credentials.
Bhudhi cannot perform tool calls directly in Phase 1.
Bhudhi cannot call APIs, send notifications, create orders, or update state by itself.
All state-changing actions must be executed by normal engines after validation.
Admin/internal Bhudhi calls must still be logged and output-validated.
User-facing outputs must be sanitized before display.

23. User-Facing Behavior
Bhudhi should feel integrated into the execution system, not like a separate chatbot floating beside it.
Bhudhi explanations must be short, direct, and tied to the user's current next action.
Bhudhi must not expose internal event names, package ids, database names, or validator language.
Bhudhi must never imply the system changed something unless the calling engine actually applied a validated change.
When Bhudhi is unavailable, the product must still function with deterministic copy and normal engine behavior.

28. Acceptance Criteria
No engine calls Bhudhi directly without the Trigger Router.
Every trigger type has a registered prompt contract and output validator.
Bhudhi receives only minimized context packets.
Bhudhi output cannot be used until schema and rule validation pass.
Bhudhi failures produce deterministic fallbacks instead of breaking the loop.
Every invocation is recorded in BhudhiLog with source, trigger, usage, status, and state version.
Forbidden modes DECIDE, MUTATE, and OVERRIDE are blocked in Phase 1.
Budget, timeout, and rate-limit controls are enforced.

31. Final Rule
Bhudhi makes Torgima more intelligent only when it remains controlled. The Trigger Router is the boundary that protects the system from random AI behavior. Every Bhudhi call must have a reason, a route, a context packet, a contract, a validator, a log, and a fallback. Intelligence is useful only when execution remains governed.
