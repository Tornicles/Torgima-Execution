Scenario E2 — Archetype Divergence
Run validation twice with identical goal, purpose, timeframe, commitment — but location A = Germany and location B = Nigeria. Assert that primary_archetype differs, economy_briefing text differs, at least 3 score values differ by > 1.0, and competitor_analysis returns different competitor contexts.

Scenario E3 — Blocked Validation
Run validation that produces reality_score < 2.5. Assert verdict = &apos;blocked&apos;. Attempt POST /api/v1/blueprints/launch. Assert 400 response with reason containing &apos;blocked&apos;. Assert that UI Blueprint Level Selection screen is not reachable. Assert that system_health_logs contains no entries for this attempt (it is not a system error — it is correct behaviour).

Scenario E4 — Fallback Resilience
Set ANTHROPIC_API_KEY to an invalid value. Run a full validation. Assert all 9 engines complete. Assert validation has reality_score (not null). Assert all 10 BhudhiLog entries show outcome = &apos;fallback_used&apos;. Assert the validation report shows &apos;intelligence_limited&apos; flag. Assert blueprint can still launch from fallback validation.

Scenario E5 — Smoke Test to Normal Execution Transition
Use erectorBlueprintLaunched fixture. Complete all 7 smoke test tasks sequentially, submitting valid feedback after each. After task 7 completes and feedback is submitted, assert that the task generation worker creates a new task with generation_reason != &apos;erector_first_week_seed&apos;. Assert the Smoke Test indicator is no longer visible on the new task. Assert signal snapshot is created after task 7 feedback.

Scenario E6 — Idempotency
POST /api/v1/validation/run with idempotency_key = &apos;test-key-001&apos;. Note validation_id returned. POST the identical request again with the same idempotency_key. Assert the same validation_id is returned. Assert no new ValidationRun record was created. Assert no new Bhudhi calls were made (BhudhiLog count unchanged).
